## 4. 资源与五倍逻辑

资源口径已经明确：顶部体力为原始体力点数，顶部活动资源是原始个数，不是可挑战次数。图3实际 OCR：体力 `3.4万`、活动资源 `29`、五倍券 `0`、单次体力 `×6`、单次活动资源 `×1`。

体力图标与本地明确标注「体力」的 RichMan 商店素材匹配 0.95028；挑战下的体力图标与顶部原图形状对照，加上当前 AP 流程，确认 ×6 是体力消耗。用户明确确认 ×1 每场必扣 1 个活动资源，耗尽不能挑战。没有猜测活动资源的正式名称。

首次进入或会话失效后读取所有余额、消耗和图标，连续两帧必须相同，且五倍 OFF 与「自动」控件布局被正向确认，共读取 10 个资源 OCR 字段。稳定连续场次不重复余额 OCR，只校验已确认的静态消耗文字、图标和配置；重新导航、配置或消耗变化会使会话失效。当前仅允许成本 `(6,1)`；图标缺失、OCR 空值/异常/未知单位、不同帧不一致全部停止。不会点击资源购买、加号或通用确认按钮。

体力简写按保守下界解析：`3.4万 → 33000`，`3.45万 → 34400`，减去一个显示精度单位，避免将四舍五入值当作精确余额。临界余额可能提前停止，优先保证资源安全。普通纯数字保持精确值；`12/50`、缺单位的 `3.4`、乱码、负数等拒绝。五倍券/活动资源必须纯整数；不使用替换字母、抽取所有数字的宽松修正。

验证时任一余额不足单场成本就正常停止，不尝试购买。缓存只保存会话配置和静态消耗，不缓存或推算当前余额，也不按 1/5 预扣。每次发起前检查时间、次数、会话有效性和挑战控件稳定性。实际资源耗尽时，通过同帧模板候选和精确 OCR `琥珀卷轴不足` 正常停止；漏检且未入场则有限等待后安全停止，不重复点击挑战。

五倍配置必须 False；实际 ON 时只点击一次已识别的 ON 开关，8 秒内确认 OFF，否则停止。UNKNOWN 不点击；不会主动开启五倍，也不修改 pass 等模式的旧行为。首轮不用五倍券。

## 5. 完整状态机

| 状态/转换 | 成功条件与操作 | 超时/安全退出 |
| --- | --- | --- |
| 庭院 → 活动主页 | 庭院标识 + 本期图标；动态点击后新帧确认 HOME | 总导航35秒、刷新8次、入口3次；缺图标/刷新按钮/未知弹窗停止 |
| 活动主页 → 挑战页 | 主页标题 + 六字；文字矩形单击；直接确认古迹演武标题/挑战按钮/资源图标 | 最多3次 HOME 点击；没有旧中转页 |
| 挑战页 → 入场 | 限制未到、有效资源会话、锁定/预设规则、OFF；挑战控件至少 3 个新鲜帧且连续稳定 0.9 秒后只点一次 | 稳定等待最多8秒；入场25秒，期间不再次点挑战；截止后再取一帧检查是否已入战 |
| 已开始战斗/准备 → 通用战斗 | 复用 GeneralBattle 计数、主题识别、阵容预设；真实战斗被识别后接管 | 原准备助手25秒等待，局部截图截止30秒约束其内层循环；失败抛异常，避免父类忽略 False |
| 战斗 → 胜利 | 原真实战斗识别；专属胜利和继续，连续两帧稳定才允许单击 | 战斗/结算总240秒；UNKNOWN连续12秒停止；不随机点击/滑动战斗 |
| 胜利 → 奖励 | 安全全屏随机单击一次；重新取帧；奖励标记和继续确认 | 不同阶段间隔至少0.8秒；同阶段重试至少2秒、最多3次；阶段累计30秒；未知页只等待不点 |
| 奖励 → 挑战 | 第二次安全单击；挑战联合特征连续两帧 | 未看到奖励不宣告成功；达到点击次数也不能成功；异常保存现场 |
| 挑战 → 下一场/结束 | 只有上述确认返回才增加完成数；下一场检查限制、资源会话和控件连续稳定 | 达 ap_limit/总时间/确认资源不足，不新开战；正常结束用活动局部返回到庭院，每步12秒 |

次数语义沿用通用战斗：`current_count` 在进入通用战斗时计一次尝试；本次另外的 `_ap_completed` 仅在确认奖励后回到挑战页时递增。失败不会伪装为成功。正常开始的战斗不因时间/次数限制中断，完成后再停止。

恢复：已在真实战斗/准备/胜利时接管；若启动时已经处于奖励页，明确标记为结算恢复，允许奖励→挑战收口，仍需连续两帧挑战确认。本轮正常入场要求先胜利后奖励；不能把未见胜利的任意奖励页当作正常战斗成功。恢复尝试计入本次上限，日志里不会推断此前已耗资源数。

AP 截图入口保留 HOT 更新与设备截图/保护，但不调用 BaseTask 的自动勾协处理，避免截图期间额外点击。未知邀请/遮罩导致识别失败会安全停止；其他任务仍走原截图链。公共模块没有改动。

`ap_wait_challenge_ready()` 最多等待8秒，使用持续取得的新鲜帧。挑战页联合特征、五倍 OFF、期望的锁定/解锁且无相反状态、挑战按钮、两个消耗图标和自动控件均满足后，必须至少3帧且连续稳定0.9秒，才允许一次挑战输入。

稳定性对照锚点帧：按钮 ROI 各坐标/尺寸偏移不超过2像素、按钮区域尺寸相同、平均绝对亮度差不超过12、归一化相关度不低于0.97，并保持相同会话配置。控件缺失、页面闪烁、位置/亮度/配置变化会重置稳定窗口；五倍配置启用、未知确认或失败页直接安全停止。等待中检测到已经进入准备/战斗/结算则接管，不补点挑战；时间或次数到限不发起新输入。稳定等待不增加资源 OCR，发起前仍复核已验证的资源会话和限制。

这是一段视觉稳定等待，不代表 Windows 输入后端或游戏已经接受点击。单次输入后仍按当前25秒入场观察、最后一帧接管和超时安全停止处理，不重试挑战，也不根据未扣资源推断没有待处理请求。

### 当前诊断机制

所有诊断使用 `AP_GUJI_TRACE`，不改变原匹配结果或输入决策：

- `session_miss`：记录第一个失败原因、会话配置或失败规则、定位 ROI、NCC/阈值和 MAE/阈值；只在同一现有帧重算失败规则的度量，不重复调用 `RuleImage.match`、不移动 ROI、不补 OCR、不继续执行后续会话检查。
- `fire_input`：记录原始1280×720坐标、控制方法、请求时间、后端返回时间、调用耗时及返回/异常状态；可取得的窗口坐标换算标为返回后的投影。后端没有暴露的按压时长、输入是否真正发送等字段明确标为 `not_exposed`，`game_acceptance=unconfirmed`；后端返回不是游戏确认。
- `entry_state`：记录状态变化、观察耗时、连续同类状态帧数，以及3秒待入场和截止帧。分类器没有暴露连续数值置信度，明确记录 `confidence=not_exposed_boolean_classifier`，不伪造概率。
- 若单次挑战后3秒仍未确认入场，保存输入前保留帧和当前待入场帧；入场超时继续保存现场。正常轮次不额外生成这两张诊断图。保留 `first_seen`、两阶段结算输入/返回、`fire_intent`、`fire_delivered`、`entry_confirmed` 等时序日志。

新增诊断经过 `ap_diagnostic_trace()` 隔离，度量和元数据读取失败仅记录错误类型，不把诊断失败变成识别或输入失败。本轮按当前源码核对上述机制，没有修改其实现。
