# 绘卷模式与活动流程审计

更新日期：2026-10-02。来源：S1–S3及当前 be4160d 静态核查；[来源登记](README.md#sources)。

## 1. 业务边界

当前“绘卷模式”跨越多个模块：

| 模块 | 职责 |
|---|---|
| MemoryScrolls | 进入活动、选择绘卷、检查小碎片/进度、捐献、返回和排程 |
| Exploration | 探索地图目标选择、刷取和绘卷模式联动 |
| RealmRaid | 突破票对应的个人突破流程 |
| GeneralBattle | 战斗结果、奖励页面、安全点击和返回 |

MemoryScrolls 不是地图战斗模块。“绘卷识别高价值怪物”应落在 Exploration 的目标选择层，而奖励判断在共享结算层。

## 2. 当前 MemoryScrolls 实现

主要文件：[script_task.py](../../tasks/MemoryScrolls/script_task.py)、[config.py](../../tasks/MemoryScrolls/config.py)、[assets.py](../../tasks/MemoryScrolls/assets.py)。

```text
召唤页 → 绘卷入口 → 可选活动选择
  → 可选小碎片满50检查 → 选择分卷
  → 可选进度OCR与联动 → 可选全量捐献
  → 关闭捐献页 → 返回 → TaskEnd
```

| 能力 | 当前情况 | 限制 |
|---|---|---|
| 双绘卷 | DoubleScrolls 支持选择活动 | 选择其中一个，不是一次遍历两套 |
| 分卷 | ScrollNumber 和对应点击区域 | 沿用当前六个分卷选择 |
| 小碎片满 50 | I_MS_FRAGMENT_S_50 固定模板 | 是局部数量判据，不是整个活动结束 |
| 进度 | O_NUMBER 及个人进度分段策略 | 开启通知时也影响探索启停和时长 |
| 捐献 | 自动捐献可用碎片，以零数量/动画判断 | 无 yys 式排名和目标积分配置 |
| 收尾 | 分段返回及 TaskEnd | 自身下一次排程未覆盖全部成功路径 |

小碎片未满分支当前会按失败结束本次检查。未来应先确认“检查条件未满足”是正常 no_work 还是业务失败，不照搬外部结果。

## 3. 问题与最小修改

| ID | 优先级 | 当前事实/风险 | 最小方向 |
|---|---|---|---|
| MS-01 | P0 | run 没有所有路径统一的自排程；满 50 先安排明日探索，后续进度分支可能安排现在 | 收集状态后集中作最终决定，每个受影响任务只写一次 |
| MS-02 | P0 | auto_close_exploration 嵌套在 notification_95 中；通知也修改探索开关/时长 | 通知与业务控制分离，保留明确个人策略 |
| MS-03 | P0 | 数字 OCR 空结果可能变成 0，进度分支将其当低进度启用探索 | 区分无效读数与有效零，校验范围并有限复核 |
| MS-04 | P0 | 入口、分卷、数量和捐献动画等内层循环缺局部硬总期限 | 共享本阶段截止时间，超时明确未完成 |
| MS-05 | P1/静态风险 | 捐献条件含 I_MS_CONTRIBUTE OR NOT I_MS_COMPLETE，完成模板失配也可进入捐献逻辑 | 使用正向页面证据，补零碎片/完成/失配负例 |
| MS-06 | P1 | 捐献结束无明确成功/超时结果，依赖三个零数量模板 | 区分 no_work、确认捐献、超时、页面错误；需要时验证增量 |
| MS-07 | P1 | 缺明确活动不存在、已结束和加载失败状态 | 少量正向判据及有限返回，避免入口反复查找 |

S1/S2 已隔离复现排程和通知耦合问题；本轮确认源码仍有对应路径，但未再次运行复现。MS-01 是某些配置/路径下可能重复，不能写成所有运行必然立即重入。

最终决策要区分活动结束、每日配额、进度策略、普通完成和失败退避。失败不能伪装为普通完成；满 50/活动结束不能被后续恢复探索覆盖。普通禁用任务与允许活动自动启停之间的产品语义须先明确。

## 4. 达摩与高价值目标识别

已确认：Exploration 有单个达摩 UP 模板，表示加成标记。S2 查看图片及哈希后确认两边使用相同标记。

未确认：白/红/黑达摩独立分类、可靠特殊奖励身份、现成的价值/稀有度评分。达摩购买或战后奖励模板不等于探索目标分类能力。

低成本可行方向：

1. 先确认地图和目标所在区域。
2. 用现有模板或少量变体在局部 ROI 识别可见标记。
3. 在同一帧中关联攻击按钮，关联失败不降级普通目标。
4. 只有目标身份有可靠证据时才应用用户优先规则。
5. OCR 只在文字参与决策时使用；颜色作为辅助，不能凭颜色直接推断高价值目标。

## 5. 战斗奖励与结算

正确共享路径：[general_battle.py](../../tasks/Component/GeneralBattle/general_battle.py)、[reward_frame.py](../../tasks/Component/GeneralBattle/reward_frame.py)。

| ID/场景 | 当前事实或风险 | 保留/改进方向 |
|---|---|---|
| 胜败识别 | 多种胜利模板、失败模板和退战路径 | 主动退战独立于真实败北 |
| 安全领取 | 奖励框、禁点区、共享冷却、部分按帧缓存 | 保留，不以加速为由绕开 |
| GB-01 金币独命中 | 初段接受金币为胜利，面板门控只等普通奖励/详情；S2已复现未领奖返回成功 | 贯通金币奖励判据，确认领取后结束 |
| GB-02 奖励网格 | 后段兜底可达，首段未具备相同入口 | 在战斗上下文内验证兜底，防其他网格误判 |
| 返回证据 | 单帧奖励标记/网格消失可能落在过渡帧 | 稳定确认或正向目标页面 |
| 未知弹窗/追加点击 | 部分旧随机点击与连续点击没有逐次页面确认 | 按风险限定，沿用安全区域和冷却 |

yys 的 I_WIN_4 与 I_FALSE_4 指向同一失败图。不能原样增加胜利模板数量，更不能据此认定其结算更准确。

## 6. 外部优势与不足

| 来源/设计 | 借鉴价值 | 需要防护 |
|---|---|---|
| yys 排名门控 | 达到目标排名后减少不必要捐献 | 无效 OCR 不能当排名 0，排名随时间变化 |
| yys 目标积分与前后差值 | 捐献有预算和效果反馈 | 达到/超过目标可能超额，非精确零超额 |
| yys 独立结束动作 | 活动结束与通知分开 | 开关和多任务关闭不能直接移植 |
| yys 捐献计时 | 有外层时间约束思想 | 内层动画循环仍可能无期限 |
| 官方普通排程/独立关闭 | 修复当前成功收尾缺口 | 官方也有无期限循环及未满失败语义 |
| 官方 dev 生命周期 | 明确阶段与终态 | 不整体替换当前安全结算 |

yys 没有完整解决满 50、重复进入、页面卡死和准确完成；它是局部参考。

## 7. 低资源占用策略

| 场景 | 策略 | 安全边界 |
|---|---|---|
| 同页面多判据 | 复用当前截图 | 点击/页面变化后重新截图 |
| 满 50 | 页面门禁＋局部模板优先，必要时局部 OCR | 不用旧帧或上一活动数据 |
| 进度/排名 | 页面稳定后或有业务需求时读取 | 已结束不读排名；功能关闭不做对应 OCR |
| 捐献确认 | 前后必要数量/积分读取 | 空读不是零，动画失效不能记成功 |
| 模板 | 延迟加载、少量候选和有限 ROI | 主题/活动切换清对应缓存 |
| 日志 | 状态变化、重试与最终摘要 | 保留失败诊断 |
| 自动退出 | 确认终态后走有限返回路径 | 不靠一帧消失或无限盲点 |

没有统一实测支持 yys 更省 CPU/内存。新增排名 OCR 甚至可能增加消耗，应按同设备同场景验证。
