# OAS Personal：优化路线

更新日期：2026-10-02。来源：S1–S4及本轮静态核查。本页是计划，不是已实现功能清单；[来源与证据](README.md#sources)。

## 优先级与阶段

| 优先级 | 定义 | 原则 |
|---|---|---|
| P0 | 正确性、任务完成、奖励领取或必要恢复受影响 | 先复现，再最小修复；新 P0 优先于功能建设 |
| P1 | 减少重复操作、等待、误判和无效资源消耗 | 用任务结果与运行数据验收 |
| P2 | 资源组织、状态边界和未来维护能力 | 局部试点，默认保留原行为 |

S1 曾使用不同优先级定义。本页统一采用后续审计与 Roadmap 的 P0/P1/P2，变更分级不改变原事实。

旧 Roadmap 的 Phase 1–4 在本页重新归入用户要求的 Phase 0–3；没有四套并行实施计划。P0 不因复杂而推迟到架构升级。

“适合 Codex”指任务范围获得授权后能够实施和验证，不代表允许自动操作真实账号、更新生产目录、提交或推送。实际权限以用户本轮指令和 AGENTS.md 为准。

|---|---|---|---|---|

| 同帧识别复用与变化日志 | P1 | Exploration 场景调用、庭院奖励 helper、关键业务日志 | 低—中；点击后必须失效 | 是，分调用点实施 |

| MD-06/MD-07：已完成庭院收尾、登录收获交接 | P1 | courtyard 终态门控、Restart.harvest 调用策略 | 中；必须确认完成证据 | 是；不重复添加已有重试登录复用 |
| EX-04：正常 TaskEnd 不做错误归档 | P1 | Exploration/solo.py 异常包装 | 低—中；保留真实错误证据 | 是，验证正常与异常路径 |

## Phase 3：架构升级（局部演进）

目标：吸收职责划分，减少隐式状态，不更换当前生产框架。

| 任务 | 优先级 | 修改范围 | 风险 | 是否适合 Codex 自动处理 |
|---|---|---|---|---|
| 局部 Session | P2 | 一个任务的账号、页面、帧号、截止时间和尝试预算 | 中高；共享引用和失效 | 先设计评审，再单模块试点 |
| Navigator 条件组合与失败诊断 | P2 | 现有 GameUi 的局部辅助能力 | 高；保留 overlay、庭院和登录行为 | 不适合无人审查整体迁移 |
| Battle 生命周期 | P2 | 现有安全结算外层的阶段与结果 | 高；终态和实例隔离 | 分阶段适配，不整体替换 |
| 任务结果适配逐步推广 | P2 | 已验证试点向其他任务扩展 | 中高；历史 None/TaskEnd 兼容 | 是；一次一组任务 |
| 简单可解释目标评分 | P2 | Exploration 已可靠识别的候选排序 | 中高；输入质量决定收益 | 先记录评分，再启用选择 |

验收：新辅助层减少了实际重复分支，保持旧接口；识别器、状态和预算不会跨账号泄漏。无法可靠观测的稀有度、距离或掉落收益不进入评分。

## AI 成本与执行约定

沿用 S4 的能力等级，不把型号和价格固化进长期路线：

| 等级 | 用途 |
|---|---|
| L1 | 文档、JSON、明确搜索、日志和样本整理 |
| L2 | 已知原因的局部修改与离线回归；日常默认档 |
| L3 | 完成契约、恢复调度、共享战斗、配置隔离与状态设计 |
| L4 | 关键架构独立复核、跨模块疑难调试；少量使用 |

先用较轻模型收集证据；高等级决定复杂边界；方案固定后降低实施等级。P0 不自动等于 L4。不重复跑整仓审计来解决单个已知缺陷。

每项任务采用：只读核查 → 具体方案 → 授权范围内最小修改 → 离线/日志/必要实机验证 → 获得相应授权后独立提交。详细流程见 [长期维护策略](07_Future_Maintenance_Strategy.md)。
