现有 [Upstream 策略](../Upstream/README.md)将 FLAG 列为 Primary，yys 和 runhey 列为 Reference。以下沿用这个维护定位；Reference 仍可提供值得吸收的修复。该定位不证明各来源性能或当前代码归属。

| 来源 | 跟踪重点 | 吸收方式 |
|---|---|---|
| runhey 官方 master | 活动 UI、资源、新任务、明确业务修复 | 逐项评估；资源也须样本和身份验证 |
| runhey 官方 dev | Navigator、状态边界、战斗生命周期 | 优先借鉴思想；按局部试点适配 |
| FLAG12321 run_now_2（主同步参考） | 与历史生产基础接近的日常、切号、配置变化 | 优先核实已上游化功能，避免重复引入 |
| Gitee yys run_now | 绘卷排名/积分、活动规则、多模板设计 | 读取可审计源码；编译模块不进入生产迁移 |

上述分支名来自固定审计或历史记录。每次跟踪重新核实分支存在性、目标 SHA 和变更内容，不能据此断言未来远端状态。

当前本地仅确认 origin 指向 Personal。建议未来使用彼此明确的 upstream-runhey、upstream-flag、upstream-yys 名称；**本轮没有添加这些远端**。

## 2. Personal 初始快照的特殊处理

本轮整理开始时，main 是单个初始基线提交；后续文档提交不补足此前的上游历史。不要假设它和任何上游保留共同祖先，也不要把第一次上游差异统计当成全部个人改动。

首次吸收前应：

1. 核实 Personal 基线对应的历史 FLAG/官方树。
2. 区分继承代码、已上游化改动、个人业务增强、运行数据与本地测试。
3. 建立受保护路径和功能清单，记录来源 SHA。
4. 对目标修改作逐文件/函数比较；没有可靠祖先时采用审查后的局部实现。

## 3. 每周检查清单

每周做一次有边界的检查；没有相关变化时只记录结果，不制造修改任务。本页不代表已建立定时自动化。

| 检查项 | 关注的问题 | 产出 |
|---|---|---|
| 远端分支与提交 | 分支改名、强推、维护方向变化 | 来源、分支、旧/新 SHA |
| Exploration / MemoryScrolls / RealmRaid | 结束条件、资源不足、联动和退战策略 | 可吸收修复或需要验证项 |
| GeneralBattle / GameUi | 新奖励、弹窗、返回页面、导航变化 | 是否触及安全点击或个人恢复 |
| 活动与主题资源 | 新按钮、模板、ROI、枚举编号 | 资源身份和适用场景 |
| 配置/schema | 字段删除、更名、默认值、保存方式 | 旧配置兼容风险 |
| OCR/依赖/设备 | 模型、线程、Python 和截图接口 | 是否需要隔离环境验证 |
| 更新器 | 目标分支、manifest、保护清单、正式状态假设 | 是否仍适配 Personal |
| 本地验证与日志 | 新异常、重复执行、冷加载、耗时变化 | 有证据的下一项任务 |

记录采用“来源/版本 → 实际变化 → 本地需求 → 决策 → 验证要求”，不重复全文复制上游公告。

## 4. 选择性吸收 PR/提交

### Step 1：只读分析

先读取本审计入口、相关模块页、真实文件和 Git 状态。查看上游 diff、依赖提交和测试，区分修复、资源适配、功能扩展和架构变化。

PR 被合并或来自官方，不自动证明适合 Personal。检查当前是否已具备等价修复，避免重复代码和行为回退。

### Step 2：具体方案

写明修改文件/函数、行为差异、配置兼容、保护边界、验证和回滚方式。选择：

- 只吸收思想：接口不同或当前实现已有更强保护。
- 局部适配：修复清楚、依赖有限、可单独验证。
- 选择性提交迁移：共同基线与依赖确实可用，仍须审查结果。
- 不吸收：内部不可审计、收益不明确或会覆盖核心增强。

### Step 3：隔离实施

用户授权范围内，使用独立功能分支或合适的隔离 checkout。当前存在个人修改时，先保护和区分，不能 reset/clean 使目录“干净”。每个任务只处理一个问题，不顺带同步整个上游目录。

### Step 4：验证

先运行直接相关的最小必要验证，再做业务日志和授权范围内的实机观察：

| 影响范围 | 必要验证 |
|---|---|
| 目标筛选 | 无目标、错配、多个目标、加载过渡帧 |
| 多账号/恢复 | true/false 组合、部分失败、重试、跨日、配置变化 |
| 结算 | 胜利、失败、主动退战、金币/普通奖励、弹窗、返回 |
| 资源/主题 | 正负样本、默认恢复、账号切换、错胜败图、旧编号 |
| 配置持久化 | 外部编辑、并发、身份变化、写入中断、旧格式 |

历史审计的 85/48 项结果不能替代当前基线验证。新模型、新资源或共享接口没有被原用例覆盖时，明确写出缺口。

### Step 5：提交与部署

通过验证后提交一个明确目的的变化，记录来源提交/PR、适配原因、验证和局限。commit、push、PR 和生产更新分别需要对应授权；已授权步骤不逐行重复询问。

按照 [AGENTS.md](../../AGENTS.md)，正式修改遵循确认后的范围，未经授权不提交、推送或创建 PR。本页和文档生成不授予未来代码、Git 写入或更新权限。

## 5. 防覆盖措施

- 保护 ConfigStore、多账号核心调度、OCR 底层、安全结算和安全更新工具；修改这些边界时提供明确收益与完整相关验证。
- 不迁移账号配置、task_plan.json、进度、generations、toolkit 或私密通知参数。
- 主题按名称和稳定身份映射，不按外部 Main15/Main17 等编号直接覆盖。
- 不直接导入自动生成 assets.py；先核实源 JSON、图片、ROI 和运行接口。
- 上游已经实现的公共功能从个人差异中移除重复实现，但必须证明行为和配置兼容。
- 回滚针对当前任务的独立提交，保留后续用户修改；有运行数据变化时单独设计数据恢复。

## 6. 安全更新器过渡

仓库外安全更新器已有候选、Formal Cutover、运行数据保护和失败恢复设计，但 README/manifest 含历史分支与基线假设。本轮没有执行 DryRun、BuildCandidate 或 Execute。

在 Personal main 上启用前必须确认：

1. 正式仓库识别、分支、HEAD/index 验证是否接受 Personal。
2. 目标 RESULT 是否保留当前个人增强，而不是按旧 patch 白名单重建。
3. 运行数据、配置身份和 toolkit 是否继续受保护。
4. 失败时文件、Git 元数据和个人数据恢复是否匹配新基线。
5. 候选验证结果是否足以允许生产切换。

这是独立的 UPD-01 任务。仅有工具存在或旧 DryRun 成功不能证明现在可直接执行。
